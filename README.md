# Constella

Constella is a distributed quorum-based key-value store inspired by Dynamo-style distributed systems, written in C++17.

It supports:

- Consistent hashing with virtual nodes
- Configurable replication factor
- Quorum-based consistency (N/W/R)
- Coordinator-based request routing
- Idempotent distributed writes with TTL-based deduplication
- Heartbeat-based failure detection and dynamic node membership
- Length-prefixed TCP framing for reliable message delivery
- WAL-based persistence for crash recovery
- Multi-threaded TCP networking
- Dockerized distributed deployment with persistent volumes

---

# Architecture Overview

```text
                ┌───────────────┐
                │    Client     │
                └──────┬────────┘
                       │
                 TCP Request
                       │
              ┌────────▼────────┐
              │  Coordinator    │
              │      Node       │
              └────────┬────────┘
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
   Replica 1      Replica 2      Replica 3
```

Each node in the cluster:

- Accepts client requests
- Acts as coordinator for incoming requests
- Replicates data to responsible nodes
- Participates in quorum reads/writes
- Monitors node liveness using heartbeat messages
- Persists writes to a Write-Ahead Log

# Features

## 1. Consistent Hashing with Virtual Nodes

Constella uses a consistent hashing ring with 150 virtual nodes per physical node to distribute keys evenly across the cluster.

Benefits:

- Deterministic key placement
- Statistically even load distribution (~33% per node in a 3-node cluster)
- Minimal key movement during node changes
- Balanced failure load — when a node dies, its keys spread evenly across survivors rather than overwhelming a single node

Replica nodes are selected by walking clockwise on the hash ring with physical node deduplication.

---

## 2. Replication

Each key is replicated across multiple nodes using a configurable replication factor.

Default configuration:

```text
N = 3  (replication factor)
W = 2  (write quorum)
R = 2  (read quorum)
```

This satisfies the strong consistency rule `W + R > N`.

---

## 3. Quorum Consistency

Constella implements Dynamo-style quorum logic.

Parameters:

```text
N = Replication Factor
W = Write Quorum
R = Read Quorum
```

Consistency rule:

```text
W + R > N
```

Coordinator nodes collect W acknowledgements for writes and R values for reads before responding to the client. Replica nodes respond with local results only, using a local quorum of 1.

---

## 4. Coordinator-Based Routing

Any node can receive a client request. That node becomes the coordinator and:

1. Computes responsible replicas via the hash ring
2. Forwards requests to replicas
3. Collects acknowledgements
4. Returns final response to client

---

## 5. Idempotent Distributed Writes

Constella uses request IDs to prevent infinite replication loops, duplicate writes, and retry amplification. Each request is tagged with a unique ID generated by the coordinator.

Processed request IDs are tracked with timestamps and evicted after 60 seconds via a background cleanup thread, keeping memory usage bounded regardless of uptime.

---

## 6. Length-Prefixed TCP Framing

All inter-node and client communication uses a 4-byte length-prefixed message framing protocol:

```text
[ 4 bytes: message length (network byte order) ][ N bytes: message content ]
```

This ensures:

- Complete messages are always received regardless of TCP segmentation
- Large values (up to 1MB) are handled correctly
- Message boundaries are never ambiguous
- No silent truncation or coalescing bugs

---

## 7. WAL-Based Persistence

Every write is appended to a Write-Ahead Log before being applied to memory:

```text
PUT user1 arpan
PUT foo bar
PUT key0 valuekey0
```

On node startup, the WAL is replayed to reconstruct in-memory state. Data survives container restarts via Docker named volumes mounted at `/data`.

---

## 8. Heartbeat-Based Failure Detection

Nodes periodically exchange `PING`/`PONG` messages every 2 seconds. If a node becomes unreachable:

- It is marked dead
- Removed from the hash ring
- Excluded from replica selection

When a node recovers, it is automatically re-added to the ring. This enables fault-tolerant operation with no manual intervention.

---

## 9. Multi-threaded Networking

Constella uses POSIX TCP sockets and `std::thread` to handle:

- Concurrent client connections
- Inter-node communication
- Background heartbeat monitoring
- Background WAL cleanup

---

## 10. Dockerized Deployment

The cluster runs as multiple Docker containers using Docker Compose with named volumes for WAL persistence.

```bash
mkdir build

cmake ..
make
```

# Docker Deployment

Start the distributed cluster:

```bash
docker compose up --build
```

This launches node1, node2, and node3 inside isolated Docker containers with persistent WAL volumes.

Use the Python client:

```bash
python3 client/client.py 6000
```

```text

OK
```

## GET

```text

```

# Persistence Testing

Write data, restart the cluster, verify data survives:

```bash
# write data
python3 client/client.py 6000
> PUT persistent_key hello_world
OK

# restart cluster
docker compose restart

# read it back
python3 client/client.py 6000
> GET persistent_key
VALUE: hello_world
```

---

# Failure Testing

Stop a node:

```bash
docker stop constella-node2
```

Heartbeat detection automatically removes the node from the hash ring within 2 seconds. Reads and writes continue using remaining replicas. When the node restarts, it rejoins automatically and replays its WAL.
